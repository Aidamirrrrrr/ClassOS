# Найденные нестыковки и открытые вопросы

Составлено при первом сквозном чтении `product/01`–`architecture/04`–`specs/05` (2026-09-03). Ничего критичного, но стоит осознанно закрыть до начала кодирования соответствующей части, чтобы не тащить неоднозначность в implementation.

## 1. Несовпадение имён файлов с внутренними самоссылками — исправлено

Документы 3, 4, 5 указывали в шапке собственное имя файла (`03_EXECUTION_PLAN_90_DAYS.md`, `01_TECHNICAL_ARCHITECTURE.md`, `T0_SERVICE_SESSION_HOST_SPEC.md`), но физически лежали как `1.md`...`5.md` без папок. **Исправлено** в рамках этой сессии: файлы перемещены в `docs/product/`, `docs/architecture/`, `docs/specs/` с полными путями в шапках. См. `docs/README.md`.

## 2. Название крейта протокола: `agent-protocol` vs `protocol`

`product/01_ROADMAP.md` §43 в предложенной структуре агента называет крейт `agent-protocol`:

```text
agent-service
agent-session
agent-core
agent-protocol
windows-platform
```

Но `architecture/01_TECHNICAL_ARCHITECTURE.md` §14–16 и `specs/T0_*` (везде) используют имя `protocol`. **Рекомендация:** считать `protocol` каноническим (он используется в implementation-ready T0 spec, более позднем и детальном документе) — `01_ROADMAP.md` §43 в этой части устарел. Явного ADR не требуется, это просто именование крейта, но стоит one-line правкой синхронизировать `01_ROADMAP.md`, если он будет использоваться как reference при онбординге новых агентов.

## 3. Расхождение репозиторных layout'ов между документами

Три разных снимка структуры репозитория:

- `product/01_ROADMAP.md` §43 (§ "Структура") — минимальный набор крейтов.
- `product/03_EXECUTION_PLAN_90_DAYS.md` §9 — `apps/teacher`, `apps/admin`, `services/cloud`, `crates/{agent-service, agent-session, agent-core, protocol, windows-platform, common}`, `packages/{ui, api-client, shared}`, `installer/`.
- `architecture/01_TECHNICAL_ARCHITECTURE.md` §14 — расширенный набор крейтов: добавлены `transport`, `screen-capture`, `remote-input`, `policy-engine`, `software-manager`, `device-health`, `updater`.
- `specs/T0_*` §8 — только 5 крейтов (`agent-service`, `agent-session`, `agent-core`, `protocol`, `windows-platform`) — сознательно урезано под scope T0.

**Это не ошибка**, а естественная эволюция: T0 намеренно минимален, остальные крейты (`screen-capture` — T2, `remote-input` — T4, `policy-engine` — T6, `software-manager`/`device-health` — T7, `updater` — T8) появляются по мере соответствующих milestone'ов — я явно закрепил это в спеках `T2_*`/`T4_*`/`T6_*`/`T7_*`/`T8_*`. Единственное, что стоит сделать при реализации T1 — явно решить, появляется ли `transport` как отдельный крейт уже в T1 (архитектурный RFC вводит его в контексте Teacher↔Agent), и зафиксировать в `docs/specs/README-T1.md`.

## 4. `prost-build` отсутствует в `[workspace.dependencies]`

`specs/T0_*` §6 перечисляет `prost-build = "0.14"` в списке основных зависимостей, но в примере `Cargo.toml` (§9, `[workspace.dependencies]`) присутствует только `prost`, без `prost-build`. Это не обязательно баг — `prost-build` обычно нужен только как `[build-dependencies]` внутри `protocol/build.rs`, а не как shared workspace dependency. **К уточнению при реализации Step 1 (T0)**: явно решить, объявляется ли `prost-build` в `[workspace.dependencies]` для единой версии по всему workspace, или только локально в `crates/protocol/Cargo.toml` под `[build-dependencies]`.

## 5. Ценовая модель TAM-расчётов не совпадает с предложенным прайсингом

`product/02_MARKET_AND_INVESTMENT_ANALYSIS.md`:

- §19 TAM-модель считает от **500 ₽/устройство/месяц**.
- §25 предложенный прайсинг — три тира: **399 / 699 / 999 ₽**.

Это не противоречие по сути (§25 сам говорит «цены — гипотеза для тестирования, не готовый прайс»), но при использовании этих цифр во внешних материалах (питч, лендинг) стоит явно выбрать одну базовую цифру для TAM-расчётов, иначе разные документы дают разный ARR на выходе при, казалось бы, одинаковых вводных (кол-во устройств). Не блокер для инженерной работы, актуально для будущего pitch deck.

## 6. Нумерация T-milestones в разных документах слегка расходится по смыслу «что именно входит в T2/T3»

`architecture/01_TECHNICAL_ARCHITECTURE.md` §149-160 и `specs/T0_*` §179-182 сходятся на:

```text
T0 — Service/Session Host
T1 — Teacher↔Agent Network
T2 — DXGI Screenshot
T3 — Continuous thumbnail streaming
T4 — Remote control
```

Но `product/03_EXECUTION_PLAN_90_DAYS.md` использует WEEK-нумерацию (Week 1–13), не T-нумерацию, с несколько иной группировкой (например Focus Mode — Week 6, до Device Health на Week 9, тогда как в T-серии Focus Mode стал T6 уже после T5 classroom commands). Это не ошибка — Execution Plan оперирует календарными неделями 90-дневного плана, а T-серия — техническими milestone'ами внутри Windows/agent-трека; они не обязаны совпадать 1:1, т.к. Teacher Console/business-side работы (пилоты, продажи) идут параллельно. **Я сохранил T-нумерацию как основу для `docs/specs/`** (файлы называются напрямую `T0_*_SPEC.md`...`T8_*_SPEC.md`, без отдельного порядкового префикса — см. пункт 9 ниже); при желании можно добавить таблицу-мэппинг T-milestone ↔ Week в `product/03_EXECUTION_PLAN_90_DAYS.md`, но это не создано автоматически в этой сессии, чтобы не переписывать исходный документ без запроса.

## 7. Rust edition "2024" в `specs/T0_*` §9

Требует Rust ≥ 1.85 (edition 2024 стабилизирован в этой версии). Не ошибка, но стоит явно закрепить минимальную версию toolchain в `rust-toolchain.toml` при старте реализации T0, а не полагаться на «текущий stable у разработчика».

## 8. Что не является нестыковкой, но стоит держать в голове

- Персонажи документов пишут не только для будущего кода, но и для инвестора/бизнеса (`product/02`) — при чтении ИИ-агентом для инженерной задачи не нужно тянуть оттуда бизнес-формулировки в код/комментарии.
- `product/01_ROADMAP.md` §43 и `architecture/01_TECHNICAL_ARCHITECTURE.md` дают частично разный набор Protocol-сообщений верхнего уровня (`04` детальнее) — `04` считается source of truth, `01` — исторический concept-level набросок.

## 9. Ошибки, допущенные мной в этой же сессии при реорганизации (не в исходных документах)

При первом проходе я сам ввёл проблему, о которой позже спросил пользователь, и исправил её в этом же разговоре:

- **Двойная нумерация spec-файлов.** Изначально я назвал файлы `docs/specs/05_T0_*.md` … `14_FUTURE_*.md` — сквозной порядковый номер поверх T-номера milestone'а внутри содержимого. Получилось два независимых счётчика на один файл (`10_T5_...` — файл «10», milestone T5), что заставляло держать в голове таблицу смещений вместо того, чтобы имя файла было самоочевидным. **Исправлено:** файлы переименованы без порядкового префикса — `T0_SERVICE_SESSION_HOST_SPEC.md` … `T8_INSTALLER_UPDATER_CLOUD_V0_SPEC.md`, `FUTURE_PHASES_OVERVIEW.md` без номера (это не T-milestone). `docs/architecture/01_TECHNICAL_ARCHITECTURE.md` — единственный файл в папке, оставлен с локальным `01_` (а не сквозным `04_`), т.к. под ним разумно оставить место для будущих `02_DATA_MODEL.md` и т.п. Нумерация в `docs/product/01–03` сохранена без изменений — там номер отражает реальный порядок чтения (roadmap → рынок → план), а не искусственный счётчик.
- **Пропущенный ADR.** Спека `specs/T1_NETWORK_AND_DEVICE_DISCOVERY_SPEC.md` вводит решение (enrollment через локальную Teacher Console-заглушку вместо облака), которое по правилу из `CLAUDE.md` («модель аутентификации/enrollment устройства») обязано быть оформлено ADR — но я изначально написал его прямо в spec без ADR. **Исправлено:** добавлен `docs/architecture/adr/0007-t1-local-enrollment-stub.md`, T1-спека на него ссылается.
- **Случайный `git init`.** При выполнении bash-команды на переименование файлов я по инерции добавил `git init -q` в начало составной команды — репозиторий не был git-репозиторием, и это не входило в задачу. Обнаружено и откачено (`rm -rf .git`) в течение той же сессии, до каких-либо коммитов.

Вывод: сама структура (папки product/architecture/specs, ADR, BACKLOG) осталась прежней и оправданной, но реализация нумерации внутри неё была не продумана с первого раза — стоило сразу спросить себя «что кодирует этот номер», а не нумеровать по инерции.

## 10. Открытые расхождения после сквозной ревизии кода (2026-09-04)

Найдены чтением кода, а не документов. Часть закрыта в той же сессии, часть
осознанно оставлена.

### Закрыто

- **Написанный, но никем не вызываемый код.** `PriorityQueue` (T3),
  `transport::lease::authorize` (T8) и крейт `updater` (T8) имели тесты и ноль
  вызывающих; установщик не копировал `classos-updater.exe`. Всё связано, см.
  таблицу в `specs/BACKLOG.md`.
- **Второй идентификатор устройства.** Cloud выдавал устройству собственный
  UUID вместо его `device_id` из T1, из-за чего списки устройств Cloud и
  консоли нельзя было сопоставить.
- **Эфемерный ключ издателя lease.** Cloud генерировал его при каждом старте,
  то есть все выданные lease обесценивались вместе с процессом.
- **Отсутствие таблицы `sessions` в `schema.sql`** при наличии
  `saveSession`/`findSession` в интерфейсе хранилища.
- **`citext` без `CREATE EXTENSION`** — схема не применилась бы на чистой базе.
- **Второй crypto-провайдер rustls.** Добавление HTTP-клиента включило
  `aws-lc-rs` рядом с `ring`, после чего rustls переставал выбирать провайдера
  сам, и TLS-транспорт агента падал бы в рантайме. Провайдер теперь выбирается
  явно; полагаться на автоматический выбор нельзя ни в одном крейте.

### Найдено при проверке milestone'ов против их спек

- **Каждая запрос-ответ операция консоли ломалась гарантированно.**
  `tokio::time::interval` выдаёт первый тик немедленно, поэтому агент отправлял
  heartbeat и полный health-отчёт сразу после авторизации — раньше ответа на
  запрос преподавателя. Консоль читала ровно одно сообщение и объявляла его
  неожиданным. Снимок экрана, состояние устройства, старт удалённого
  управления и classroom-команды не работали бы ни разу. Исправлено с обеих
  сторон: агент начинает отсчёт через период, консоль ждёт именно свой ответ.
- **`RepairResult` приходит перед `CommandResult`**, поэтому «Привести к
  профилю» всегда завершалось ошибкой связи (T7).
- **Allow-правила AppLocker по голому имени файла** обходились переименованием
  под standard-user, то есть главный пункт DoD T6 не выполнялся (ADR-0017).
- **`primary` дисплей определялся как первый выход DXGI**, а не как основной
  монитор Windows (T2).
- **`winget::is_available()` не вызывался**: машина без winget отчитывалась
  как машина без единой нужной программы (T7).
- **PRIMARY KEY с выражением и отсутствие `CREATE EXTENSION citext`** — схема
  PostgreSQL не применялась ни на одной базе; **jsonb аудита** возвращался
  строкой вместо объекта (T8).

### Оставлено осознанно

- **Lease не привязан к ключу преподавателя.** Он перечисляет `teacherId`, но
  подтверждает его только подписью Cloud, поэтому чужой lease того же филиала
  даёт чужие права. Спека T8 §7 привязки не определяет; вводить её без ADR
  означало бы принять архитектурное решение в обход документа. См.
  `specs/README-T8.md`.
- **Вложенные pnpm-workspace.** Корневой `pnpm-workspace.yaml` объявляет
  `apps/*` и `services/*`, но у `apps/teacher` собственный workspace и
  lockfile, а `services/cloud` собирается bun'ом — то есть корневой workspace
  фактически ничего не устанавливает. Работает, но описанной в ADR-0008
  структурой не является. Приводить к одному виду стоит одновременно с
  появлением второго JS-пакета, а не раньше.
- **Список устройств консоли не переживает перезапуск**: он строится заново из
  discovery, поэтому выключенное устройство исчезает молча. Постоянный
  инвентарь — задача Cloud, а не консоли.

## 11. Проверка готовности к runtime-прогону (2026-09-05)

Найдено при отдельном проходе «можно ли начать прогон», а не «работает ли
код». Все пять пунктов лежали в эксплуатации, поэтому ни сборка, ни тесты их
не показывали.

### Закрыто

- **Перезапуск Teacher Console отключал класс безвозвратно.** `DeviceCredential`
  и закреплённый отпечаток хранились только в памяти, а устройство, прошедшее
  enrollment, `EnrollmentRequest` больше не присылает — значит перерегистрация
  невозможна. Восстановление требовало обхода всех машин класса. Реестр теперь
  сохраняется и проверяется при загрузке. Прежняя формулировка в `README-T1.md`
  («список строится заново из discovery») описывала это как косметическую
  потерю и скрывала настоящий масштаб.
- **Адрес устройства не обновлялся из обнаружения**: запись хранила адрес
  момента регистрации, поэтому после смены IP устройство оставалось видимым и
  недостижимым одновременно.
- **Ключ издателя лежал в рабочем каталоге** приложения — запуск консоли из
  другого места создавал новый ключ и отключал весь класс.
- **Продуктовый установщик не ограничивал права на `C:\Program Files\ClassOS`.**
  Это делал только dev/CI-скрипт `install-service.ps1`, а `install-classos.ps1`
  — нет, то есть ученик со стандартной учётной записью мог подменить бинарник
  службы (threat model §115).
- **В Cloud не было способа создать первого владельца.** `createUser`,
  `createOrganization` и `addMembership` существовали в обоих адаптерах
  хранилища, но не вызывались ниоткуда, кроме тестов: развёрнутый Cloud был
  непригоден. Добавлен `services/cloud/scripts/bootstrap.ts`. Тесты не ловили
  это потому, что сами заводили пользователя напрямую в хранилище — то есть
  проверяли API в состоянии, которого в реальном развёртывании не бывает.

### Оставлено осознанно

- **Окно enrollment не аутентифицировано.** Устройство отдаёт одноразовый код
  любому, кто первым установил TLS-соединение, и принимает от него ключ
  издателя навсегда. Спека T1 §6.2 описывает ровно такой поток, поэтому это
  пробел документа, а не отклонение реализации; §114 архитектуры при этом
  обещает «all control connections authenticated». Решение принято в ADR-0018;
  реализована только локальная часть (`reset-enrollment`), протокольная — нет.
- **Подпись кода.** Требует закупки сертификата, а не изменений в коде.
