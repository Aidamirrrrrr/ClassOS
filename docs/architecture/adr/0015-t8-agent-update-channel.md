# 0015 — Канал получения обновлений агентом

**Статус:** Accepted
**Дата:** 2026-09-04

## Контекст

T8 §8 требует, чтобы устройства канала `stable` обновлялись автоматически, а
Cloud публиковал манифест с версией, URL, хешем и подписью. Крейт `updater` и
`classos-updater.exe` реализуют конвейер `verify → stage → install → health
check → rollback`, но до сих пор их никто не вызывал: служба не знала ни о
существовании манифеста, ни о том, где его взять. Нужно решить, каким каналом
агент узнаёт о новой версии.

До этого решения весь трафик между Teacher Console и агентом шёл по
собственному TLS/protobuf-протоколу из ADR-0009, и других сетевых каналов у
службы не было.

## Рассмотренные варианты

1. **Расширить protobuf-протокол сообщением `UpdateAvailable`, которое присылает
   Teacher Console.** Не требует нового транспорта, но делает обновление
   устройства зависимым от присутствия преподавателя и превращает Teacher
   Console в промежуточное звено доставки бинарников — она получает роль,
   которой у неё быть не должно (инвариант 8: Teacher не выполняет
   привилегированные действия). Ночное обновление пустого кабинета становится
   невозможным.
2. **Push из Cloud на устройство.** Требует входящего соединения к устройству
   или постоянного WebSocket к Cloud; и то и другое — новая инфраструктура ради
   задачи, где задержка в час не имеет значения.
3. **Периодический pull манифеста агентом по HTTPS с Cloud API.** Отдельный от
   protobuf-канала транспорт, зато обновление не зависит ни от преподавателя,
   ни от постоянного соединения, а недоступный Cloud означает просто «сегодня
   не обновились» — урок не затрагивается (инвариант 5).

## Решение

Выбран вариант 3. Служба периодически запрашивает `GET /v1/updates/check` у
Cloud, указывая свой канал и текущую версию, и получает манифест или пустой
ответ. Адрес Cloud и канал задаются в `config.toml`; **пустой `cloud_base_url`
означает, что проверка обновлений выключена** — устройство без Cloud остаётся
полностью рабочим.

Доверие к Cloud при этом не появляется: манифест и файл проверяются подписью
издателя, вшитой в `classos-updater.exe` при сборке релиза. Скомпрометированный
Cloud может задержать обновление или предложить чужой файл, но не может
заставить установить неподписанный бинарник.

Служба не устанавливает обновление сама: она проверяет подпись и хеш,
раскладывает манифест и файл в staging-каталог и запускает
`classos-updater.exe` отдельным процессом (§8.4).

## Последствия

- У агента появляется исходящая HTTPS-зависимость и HTTP-клиент в дереве
  сборки. Это единственный не-protobuf сетевой канал агента; добавление
  следующего потребует нового ADR.
- Cloud обязан отдавать манифест в том же JSON, который разбирает
  `updater::parse_manifest`; расхождение формата ломает обновление молча, и
  поэтому закреплено кросс-языковым тестовым вектором, как уже сделано для
  lease.
- Устройство без настроенного Cloud не обновляется вообще и не пытается —
  это осознанный режим, а не деградация.
- Проверка подписи остаётся на устройстве. Перенос её в Cloud потребует
  нового ADR и означал бы, что взлом Cloud даёт исполнение кода на всех
  устройствах.
