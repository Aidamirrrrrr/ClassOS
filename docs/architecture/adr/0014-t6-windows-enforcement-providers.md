# 0014 — Выбор Windows enforcement-технологии для T6

**Статус:** Accepted
**Дата:** 2026-09-04

## Контекст

ADR-0006 зафиксировал продуктовый слой `LessonPolicy` и трейт `PolicyProvider`,
но сознательно не выбирал конкретный механизм Windows. T6 требует реального
enforcement: заблокированное политикой приложение не должно запускаться под
standard-user, а не просто закрываться overlay'ем.

Ограничения, которые давят на выбор:

- Lesson Policy динамическая: включается и выключается несколько раз за урок,
  Focus Mode — вообще временный overlay поверх неё. Механизм с перезагрузкой на
  каждое переключение непригоден.
- Обязателен rollback (инвариант IV `CLAUDE.md`): нужно уметь снять снимок
  предыдущего состояния и вернуть его целиком.
- Ошибка в политике не должна лишать администратора машины (§68 арх. RFC).
- Учебные классы работают на разных редакциях Windows 11, включая Pro.

## Рассмотренные варианты

1. **Assigned Access (restricted user experience).** Родной kiosk-механизм,
   сам подтягивает AppLocker-правила. Но он описывает целую пользовательскую
   оболочку, а не набор правил: смена профиля требует перелогина, а
   temporary override поверх активного профиля не выражается вообще. Для
   Focus Mode, который включается на 10 минут посреди урока, не подходит.
2. **App Control for Business (WDAC).** Доступен на всех редакциях и сильнее
   AppLocker по гарантиям. Но часть типов политик применяется только после
   перезагрузки, откат ошибочной политики может потребовать физического
   доступа к машине, а цена ошибки — незагружающийся класс. Это верный выбор
   для неизменяемого base-образа, а не для профиля, который меняет
   преподаватель кнопкой.
3. **AppLocker для запуска приложений + registry/GPO для системных
   ограничений + enterprise-policy браузера для URL.** Применяется мгновенно
   без перезагрузки, имеет штатный `Test-AppLockerPolicy` для шага Validate,
   а состояние целиком выражается XML-документом — то есть snapshot и rollback
   получаются естественно. Платой является зависимость от службы Application
   Identity и ограниченная поддержка на некоторых редакциях Windows.

## Решение

Выбран вариант 3 как enforcement для T6:

- запуск приложений — AppLocker (правила публикуются локальной политикой,
  Validate выполняется до Apply, snapshot — предыдущий XML целиком);
- Settings, PowerShell, cmd, Microsoft Store, персонализация — политики в
  registry по документированным путям;
- allowlist URL — enterprise-policy Chrome/Edge, без MITM и без WFP (§76).

Assigned Access и WDAC не используются в T6. Они не отвергнуты навсегда:
Assigned Access остаётся кандидатом для будущего kiosk-режима, WDAC — для
base-образа устройства; обе технологии потребуют отдельного ADR.

`PolicyProvider` обязан отвечать на вопрос о поддержке (`check_support`) до
первого Apply. Если на устройстве enforcement недоступен (нет службы
Application Identity, неподдерживаемая редакция), политика **не применяется
частично**: команда завершается явной ошибкой, а устройство остаётся в
известном состоянии. Тихая деградация до overlay запрещена — она создала бы
ложное впечатление защиты, что хуже честного отказа.

## Последствия

- Snapshot policy — это конкретный артефакт (XML AppLocker + прежние значения
  registry), который обязан сохраняться на диск: rollback должен переживать
  перезагрузку и падение Service, иначе устройство останется заблокированным.
- Появляется зависимость от службы Application Identity; её остановка —
  диагностируемое состояние устройства, а не молчаливое отсутствие защиты.
- Break-glass снимает ровно эти два вида состояния (AppLocker-политику и
  ключи registry) и потому обязан работать локально без сети (§69).
- Часть устройств может оказаться неподдерживаемой; продуктовое решение по
  таким устройствам (блокировать продажу, требовать редакцию, использовать
  WDAC) принимается отдельно и здесь не предрешается.
- Продуктовый слой по-прежнему не знает ни одного из этих механизмов: всё
  перечисленное живёт за `PolicyProvider` (ADR-0006, инвариант X).
