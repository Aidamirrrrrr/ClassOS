# 0009 — Сетевой транспорт и discovery для T1

**Статус:** Accepted
**Дата:** 2026-09-04

## Контекст

T1 требует локального обнаружения Student Agent, а затем отдельного
аутентифицированного канала Teacher Console ↔ Agent. Discovery не является
доказательством доверия, протокол должен иметь версионируемый protobuf-контракт,
а будущая смена wire transport не должна затрагивать продуктовую логику.

## Рассмотренные варианты

1. **QUIC + TLS 1.3 сразу** — даёт независимые потоки и быстрый reconnect, но
   усложняет первый сетевой milestone и не нужен для небольших сообщений T1.
2. **TLS поверх TCP + UDP multicast discovery** — поддерживается стандартным
   сетевым стеком, достаточен для T1 и оставляет возможность перейти на QUIC за
   transport abstraction. TCP требует собственного framing и в следующих
   milestone нужно будет отдельно следить за приоритетом control-сообщений.
3. **Незащищённый TCP в локальной сети** — проще для прототипа, но нарушает
   требования аутентификации, `Discovery ≠ Trust` и security invariants T1.

## Решение

Вариант 2. Публичные объявления `ClassOSDeviceAnnouncement` кодируются
Protobuf и отправляются в IPv4 multicast-группу `239.255.67.79` через UDP-порт
`45900` с TTL `1`. Защищённый control-канал использует TLS поверх TCP и порт
`45901`; protobuf-сообщения передаются через length-prefixed framing.

Схема находится в `proto/classos_network.proto`. Общие сетевые механизмы и
будущий trait `DeviceTransport` находятся в отдельном крейте `transport`, а
решения о доверии и продуктовые состояния — вне него. На 2026-09-04 порты
`45900` и `45901` отсутствуют в реестре Service Name and Transport Protocol
Port Number Registry IANA. Ошибка bind должна быть явной; адреса и порты
остаются конфигурируемыми.

Agent начинает публиковать announcement только после успешного запуска TLS
listener. Он не должен рекламировать закрытый или ещё не готовый control-порт.

## Последствия

- Discovery остаётся намеренно недоверенным и не переносит credentials,
  токены, имена учеников или ключи.
- Teacher Console использует фактический адрес UDP-источника; поле `ip` внутри
  объявления считается только подсказкой.
- Для работы multicast сеть и Windows Firewall должны разрешать UDP `45900`;
  это требует проверки на реальных машинах и настройки установщика.
- Смена multicast-группы, портов, framing или TLS/TCP на QUIC требует обновить
  этот ADR и совместимость протокола.
