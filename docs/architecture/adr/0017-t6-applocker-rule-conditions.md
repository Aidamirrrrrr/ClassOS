# 0017 — Условия правил AppLocker: где именно разрешён исполняемый файл

**Статус:** Accepted
**Дата:** 2026-09-04

## Контекст

ADR-0014 выбрал AppLocker как механизм enforcement, но не определил **тип
условия** правил. Реализация T6 генерировала для allowlist правила вида
`FilePathCondition Path="*\Code.exe"` — совпадение по имени файла в любом
каталоге.

Это сводит на нет Definition of Done T6 (§2): проверка ведётся под
standard-user, а standard-user может записать файл в свой профиль. Ученик
переименовывает произвольную программу в `Code.exe`, кладёт её в `Downloads` и
запускает — Focus Mode «разрешить только VS Code» не выполняется. Никакой
привилегии для этого не требуется, и обход не оставляет следов.

Отдельная сложность: часть приложений каталога устанавливается и в
пользовательский профиль (`%LOCALAPPDATA%\Programs\...`). Файл, который
пользователь может перезаписать, невозможно включить в allowlist, не потеряв
смысл allowlist.

## Рассмотренные варианты

1. **Publisher-правила (по подписи издателя).** Самый прочный вариант:
   переименование ничего не меняет, обновление приложения не ломает правило.
   Но условие требует точного subject сертификата Authenticode, а он
   считывается с реального подписанного бинарника. Вписать эти строки по
   памяти нельзя: ошибка означает правило, которое либо не срабатывает, либо
   блокирует нужное приложение, и проверить это можно только на настоящей
   машине с установленным приложением.
2. **Hash-правила.** Переименование не помогает, подпись не нужна. Но хеш
   меняется при каждом обновлении приложения, то есть каждое обновление
   Chrome ломает урок до пересборки политики. Для каталога, где две позиции
   из четырёх стоят на `latest`, это неприемлемо.
3. **Path-правила, привязанные к каталогам, недоступным пользователю на
   запись.** `%PROGRAMFILES%` и `%WINDIR%` изменяются только
   администратором, поэтому подменить там файл standard-user не может.
   Слабее publisher-правил (администратор или установщик может положить туда
   что угодно), но устраняет ровно тот обход, который делает enforcement
   бессмысленным.

## Решение

Разрешающие и запрещающие правила получают **разную** широту — это не
асимметрия ради удобства, а следствие их смысла:

- **Allow** — только пути в каталогах, недоступных пользователю на запись:
  `%PROGRAMFILES%` и `%WINDIR%`. Разрешение по голому имени файла запрещено.
- **Deny** — по-прежнему `*\<имя>`: запрет обязан действовать в любом
  каталоге, иначе он обходится переносом файла.

Следствие, принимаемое сознательно: приложение, установленное **в профиль
пользователя**, политикой не разрешается. Поэтому установка пакетов из
каталога выполняется в машинную область (`winget --scope machine`), чтобы
управляемые ClassOS приложения оказывались в `%PROGRAMFILES%`.

Publisher-правила (вариант 1) остаются целью и не отвергнуты: они требуют
subject сертификатов, снятых с настоящих бинарников на реальной машине.
Переход на них — отдельный ADR после первой приёмки на оборудовании.

## Последствия

- Обход переименованием под standard-user закрыт; обход через запись в
  `%PROGRAMFILES%` требует прав администратора, то есть выходит за модель
  угроз ученической машины.
- Приложение, установленное пользователем «для себя», перестаёт запускаться
  под активной политикой. Это правильное поведение allowlist, но его нужно
  объяснять администратору школы, а не считать сбоем.
- `winget install/upgrade` для каталога всегда выполняется с
  `--scope machine`; установка в профиль пользователя перестаёт быть
  вариантом для управляемых приложений.
- Проверка `Test-AppLockerPolicy` на шаге Validate теперь проверяет не только
  синтаксис, но и то, что разрешённый файл действительно лежит в разрешённом
  каталоге — расхождение обнаружится до Apply, а не в классе.
- Список разрешённых каталогов вшит в генератор XML и не приходит по сети:
  сетевой документ политики оперирует именами приложений, а не путями
  (инвариант X).
