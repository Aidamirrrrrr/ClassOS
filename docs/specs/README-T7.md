# ClassOS T7 — device health и software management

Статус по `docs/specs/BACKLOG.md`: **код завершён и покрыт автоматическими
проверками; ни один вызов winget и ни один сбор метрик не выполнялся на
реальной машине.**

> T7 начат по явному разрешению владельца проекта при `Runtime validation:
> not started` у T6 — это отступление от правила 3 `BACKLOG.md`, а не его
> отмена. Долг по реальной приёмке T0–T7 накапливается и остаётся
> обязательным перед пилотом.

## Принятые границы реализации

```text
device-health       пороги и правила состояния, без единого системного вызова
software-manager    каталог приложений, профили, drift, repair-логика
windows-platform    примитивы: метрики Win32, вызовы winget
agent-service       сборка отчёта и маршруты команд
```

Каталог приложений теперь **один на всю систему**: `LaunchApplication` из T5,
компилятор политик T6 и software management T7 берут определения из
`software-manager`. Параллельного списка приложений в коде больше нет
(spec T7 §5) — прежний enum в `agent-core::commands` удалён.

## Реализовано

- `ApplicationDefinition` с publisher, исполняемыми файлами, `wingetId` и
  **одобренной версией**: `latest` — не значение по умолчанию, а отдельное
  решение по каждому приложению;
- approved catalog как единственный источник: произвольный package id в
  менеджер пакетов передать невозможно by design, а не по проверке;
- software-профили кабинета и расчёт drift (отсутствует / версия не та) со
  строгим сравнением префикса версии;
- Repair: install/upgrade только для расхождений указанного профиля, с
  обязательной проверкой результата после установки — «winget вернул 0» и
  «стало соответствовать профилю» считаются разными событиями;
- частичный отказ не прерывает остальные пакеты и возвращается по каждому
  приложению отдельно;
- health-правила: диск > 90% → Warning, ≥ 97% → Critical, нехватка ПО →
  Warning, сбой применения политики → Critical; худшее состояние побеждает,
  коды предупреждений машиночитаемые;
- health считается на устройстве и не требует облака (local-first);
- периодический отчёт раз в минуту плюс явный `HealthRequest`; инвентарь
  кэшируется на 15 минут, потому что опрос winget занимает секунды;
- сбор метрик и установка пакетов уходят на blocking-пул: иначе один Repair
  остановил бы стрим и heartbeat всего класса;
- Teacher Console: таблица состояния кабинета и «Привести к профилю», коды
  предупреждений переводятся в текст на стороне UI.

## Автоматически проверяется

121 unit-тест workspace, из них по T7:

- каталог не резолвит произвольный пакет и путь к файлу;
- pinned-версия не подменяется на latest;
- сравнение версий: `3.13` принимает `3.13.2`, но не `3.14.0` и не `3.1`;
- drift для типового профиля: отсутствие и несовпадение версии;
- профиль в desired state не даёт расхождений и не вызывает установку;
- repair чинит только требования профиля и проверяет результат;
- «тихая» установка без эффекта отражается как `REPAIR_VERIFY_FAILED`;
- частичный отказ не отменяет остальные пакеты;
- неизвестный профиль отклоняется;
- health: пороги, граница «ровно 90%», комбинация проблем, приоритет
  Critical над Warning;
- protobuf round-trip `DeviceHealthReport`, `RepairResult` и
  `RepairDesiredState`.

Плюс `cargo fmt`, `cargo clippy -D warnings`, Windows cross-check и Windows CI
для всего workspace и backend Teacher Console.

## Не проверено на реальном оборудовании

- ни один вызов `winget list/install/upgrade` не выполнялся; **разбор
  табличного вывода `winget list` — самое хрупкое место T7**: формат таблицы
  не является стабильным контрактом, и первая же реальная проверка может
  потребовать перехода на другой способ detection;
- сбор метрик CPU/RAM/диска и чтение версии Windows из реестра;
- поведение на устройстве без winget;
- реальная установка пакета и подтверждение через detect;
- drift после ручного удаления пакета;
- параллельный Repair на нескольких устройствах;
- время выполнения Repair и его влияние на стрим в реальном классе.

## Исправлено после сквозной ревизии

`winget::is_available()` был написан, но не вызывался: на машине без winget
любая ошибка запуска превращалась в «пакет не установлен», поэтому исправное
устройство отчитывалось как машина без единой нужной программы, а «Привести к
профилю» запускал заведомо безнадёжные установки. Теперь недоступность
менеджера пакетов — отдельный код `SOFTWARE_MANAGER_UNAVAILABLE`, состав ПО
при нём не проверяется, а Repair отказывается начинать.

Установка пакетов выполняется в машинную область (`--scope machine`):
приложение в профиле пользователя лежит в каталоге, доступном ему на запись,
и потому не может быть разрешено политикой T6 (ADR-0017).

## Известные ограничения

- Каталог из четырёх приложений (VS Code, Python, Chrome, Git) — ровно
  столько, сколько нужно для проверяемого сценария; расширение каталога не
  требует изменений кода, только записей в `CATALOG`.
- `desiredProfileId` задаётся локально в `config.toml`
  (`software_profile_id`); привязка Room → профиль появляется с Cloud v0 (T8).
- Uninstall не реализован: spec относит его к admin-роли, а ролей до Cloud v0
  не существует. Реализовывать «пока для всех» было бы прямым нарушением
  §10.2.
- `Move room` и `Open logs` из §9 не реализованы: первый требует
  Organization-модели T8, второй — отдельного решения о передаче журналов,
  которого нет в спеке.
