# ClassOS — ADR

Используется, когда инженерное или архитектурное решение подпадает под категории из `CLAUDE.md` («Когда обязателен новый ADR»):

- транспорт/протокол (proto-схема, framing, versioning);
- разделение привилегий Service/Session Host;
- модель аутентификации/enrollment устройства;
- выбор enforcement-технологии (AppLocker vs Assigned Access vs GPO/CSP vs что-то новое).

Также уместно для любого другого решения, которое дорого развернуть через полгода — на усмотрение, но лучше лишний ADR, чем недокументированное решение, вшитое молча в код.

## Шаги

1. Прочитать `docs/architecture/adr/README.md` — индекс и шаблон, узнать следующий свободный номер.
2. Прочитать существующие ADR целиком — новое решение не должно тихо противоречить уже принятому (если противоречит — это Superseded-ADR, явно указать `Superseded by NNNN` в старом файле).
3. Создать `docs/architecture/adr/NNNN-<kebab-case-title>.md` по шаблону:

   ```markdown
   # NNNN — <Заголовок>

   **Статус:** Accepted
   **Дата:** YYYY-MM-DD

   ## Контекст
   ## Рассмотренные варианты
   ## Решение
   ## Последствия
   ```

4. Добавить строку в таблицу `docs/architecture/adr/README.md`.
5. Если ADR меняет содержание уже написанного spec — обновить соответствующий `docs/specs/NN_*.md`, сославшись на новый ADR.

## Стиль

- «Рассмотренные варианты» — минимум 2, с реальными плюсами/минусами, не соломенное чучело.
- «Последствия» — не только плюсы; явно указать, чем платим и что теперь нельзя делать иначе без нового ADR.
- Короткий файл (обычно 30-60 строк) — ADR не заменяет spec, а фиксирует одно решение.
